# 交互式 HTML 报告规范

这份规范用于把“事实和观点判断”的完整审计结果渲染成一个可阅读、可复核、可分享的网页。默认目标是单文件静态 HTML，打开本地文件即可使用；用户明确要求在线应用时，才增加服务端或构建工具。

## 页面最小结构

页面应同时提供两个视图，并保持同一份数据源：

1. **原文标注**：原文标题、来源、段落编号和正文；名词、动词、形容词、副词使用稳定且可访问的颜色高亮。
2. **分析结果**：用表格呈现事实性断言、观点/解释/立场、行动建议、论题—论据—论证—结论，以及四类词性汇总。

原文视图中的每个可分析词或短语应是可点击、可键盘聚焦的按钮。浮窗至少显示：词语、词性、语义角色、论断视角、标注理由和所在原句。筛选词性或切换“词性视角/论断视角”时，不能改变原文内容，只改变视觉强调。

页面底部要有清晰的边界提示，说明哪些是原文主张、哪些尚未外部核验。分析视图底部可以显示 JSON 接口说明，帮助后续把静态示例替换为任意文章、链接或音视频转写稿。

## 推荐数据接口

页面脚本应围绕一个 `analysisData` 对象渲染，不要把同一条分析结果手写多份。字段可按内容删减，但保留这些语义：

```js
{
  appVersion: "0.4.0",
  source: {
    title: "内容标题",
    type: "文章 / X / 播客 / 视频转写 / 用户粘贴",
    url: "https://example.com/…",
    scope: "全文",
    paragraphs: [
      {
        id: "P01",
        segments: [
          { text: "未标注的原文" },
          { text: "可分析词", tokenId: "t01" },
        ],
      },
    ],
  },
  summary: {
    thesis: "一句话主旨",
    structure: ["提出问题", "给出标准", "提出建议"],
  },
  factualClaims: [
    {
      id: "F01",
      claim: "事实性断言",
      attribution: "作者主张",
      status: "待核验",
      source: "P03",
      evidence: "文内依据或证据缺口",
    },
  ],
  opinions: [
    {
      id: "O01",
      claim: "观点或解释",
      type: "定义 / 因果 / 价值判断 / 预测 / 立场",
      source: "P02",
      support: "中",
      gap: "论证缺口",
    },
  ],
  actions: [
    {
      id: "A01",
      action: "行动建议",
      source: "P04",
      boundary: "适用条件或风险",
    },
  ],
  argumentChain: [
    {
      step: "论据 / 论证 / 结论",
      content: "对应内容",
      source: "P01–P04",
      note: "审计备注",
    },
  ],
  tokens: [
    {
      id: "t01",
      word: "可分析词",
      pos: "noun",
      role: "对象或概念",
      lens: "观点视角",
      note: "说明为什么这样标注",
      sentence: "所在原句",
      source: "P01",
    },
  ],
  footerLink: {
    label: "进入苏苏的博客主页",
    url: "https://blog.brmys.cn",
  },
}
```

`source.paragraphs[].segments` 是原文的唯一展示来源：不需要高亮的片段只写 `text`，需要高亮的片段同时写 `tokenId`；按数组顺序拼接后必须与原文完全一致。这样可以避免用字符偏移切分中文文本时出现错位。四类词性可以由 `tokens` 自动去重汇总。每个 token 至少保留 `id`、`word`、`pos`、`role`、`lens`、`note`、`sentence` 和 `source`；`pos` 使用 `noun`、`verb`、`adjective`、`adverb` 或 `other`。汇总表显示频次、语义角色、论断视角和出现位置。词性不是事实/观点标签，页面文案要明确这两个维度不等价。

## 随附渲染器

`scripts/render_html_report.py` 使用 Python 3 标准库，把上述 JSON 渲染成单文件 HTML。它负责 HTML 转义、原文段落排版、词性高亮、词语浮窗、筛选按钮、分析表格、统计数字、边界提示和页底外链。使用方式：

```bash
python3 scripts/render_html_report.py references/analysis-data.example.json \
  --output 事实和观点判断-报告.html
```

渲染器不访问网络、不加载远程资源，也不会把分析内容上传到任何服务。没有 `segments` 或 `tokens` 时，它仍会生成可阅读的无高亮页面，并在页面中保留“未提供词语标注”的提示；不要为了填充高亮而编造词性。

## 视觉与交互基线

- 名词、动词、形容词、副词使用四种高对比但克制的颜色，并配合文字图例；不能只靠颜色传达信息。
- 表格允许横向滚动，长文本不强行压缩成难以阅读的窄列；段落始终按块级元素纵向排列。
- 浮窗应在视口内定位，支持关闭按钮和 `Escape` 关闭；移动端不能遮住整段正文。
- 统计数字只能来自 `analysisData`，不能手填后与表格数量不一致。
- 所有原文和分析文本都应经过 HTML 转义；如果使用 `innerHTML` 渲染表格，必须先转义单元格内容。
- 页面不依赖 CDN、远程字体或网络脚本；用户未要求时不采集、不发送阅读数据。
- 词语详情使用文本节点展示，不把未经转义的用户原文拼进 `innerHTML`。

## 版本控制

页面在页眉或页脚显示 `appVersion`，并维护页面所属项目的 `CHANGELOG.md`：

- 补丁版本：修复排版、交互或兼容性问题，不改变数据接口；
- 次版本：新增视图、表格、筛选器、页底外链等向后兼容功能；
- 主版本：改变 `analysisData` 必填字段或破坏已有页面加载方式。

修改数据接口时，同步更新本规范中的示例和页面兼容逻辑。分享链接指向仓库时保持仓库 URL 不变，只更新 Skill、模板或页面版本。

## 页底外链

只有在用户提供了主页/站点 URL，或当前项目有明确配置时，才在页面底部加入：

```html
<a href="{footerLink.url}" target="_blank" rel="noopener noreferrer">
  {footerLink.label} ↗
</a>
```

当前苏苏项目的已确认配置是“苏苏的博客主页” `https://blog.brmys.cn`。对其他项目或其他站点，不得自动套用该 URL；应沿用用户提供的主页，或省略入口并说明未配置。

## 验收清单

- [ ] 原文、来源、段落定位和分析范围完整保留。
- [ ] 原文高亮与表格来自同一份结构化数据。
- [ ] 点击词语能看到浮窗，浮窗内容与原句一致。
- [ ] 事实性断言、观点、行动、论证链和四类词性表均可查阅。
- [ ] 核验状态和证据缺口没有被视觉设计隐藏。
- [ ] 桌面端和窄屏端没有段落错位、横向溢出或不可访问控件。
- [ ] 页面版本、项目 changelog 和数据接口保持一致。
- [ ] 页底外链存在时能跳转到配置的主页，且使用新窗口安全属性。
- [ ] 若明确要求网页，最终交付的是实际 `.html` 文件，而不是只有代码片段。
- [ ] 使用随附脚本时，输入 JSON 与页面上的原文、统计和分析表保持一致。
